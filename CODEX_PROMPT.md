## 📋 ВВОДНЫЙ ПРОМПТ ДЛЯ CODEX (СКОПИРУЙТЕ ТЕКСТ НИЖЕ):

`	ext
Ты — ведущий инженер по встраиваемым системам (Embedded C++ / ESP32) и робототехнике (ROS 2 / Python).
Мы работаем над проектом 3-колесного омни-робота «Термит» (Termit Omni).

### 1. АППАРАТНАЯ АРХИТЕКТУРА РОБОТА
- База: 3-колесный Omni-робот (расположение колес 120°).
- Колеса: роликовые Omni радиусом R = 0.030 м (диаметр 60 мм).
- Радиус базы: L = 0.122 м (расстояние от центра робота до оси колеса).
- Приводы: 3 шаговых двигателя NEMA 17 с микрошагом 1/8 (1600 микрошагов на оборот). Передаточное число 1.0 (8488.26 шагов на 1 метр пути).
- Бортовой контроллер приводов: ESP32 (NodeMCU / DevKit).
  - Мотор 1 (Front F): STEP = GPIO 33, DIR = GPIO 32, EN = GPIO 21 (общий EN с Мотором 2)
  - Мотор 2 (Right R): STEP = GPIO 23, DIR = GPIO 22, EN = GPIO 21 (общий EN с Мотором 1)
  - Мотор 3 (Left L):  STEP = GPIO 19, DIR = GPIO 18 (спаян с D5), EN = GPIO 17
  - Логика Enable: LOW = питание подано (удержание), HIGH = ток снят (тишина/сон).
- Бортовой компьютер верхнего уровня: Raspberry Pi 5.
  - ОС: Ubuntu / Raspberry Pi OS с ROS 2 Jazzy.
  - Связь с ESP32: USB-Serial (/dev/ttyUSB0 @ 115200 бод, 8N1).
  - Навигация: CSI-камера направлена вверх в потолок, детектирует метки ArUco (DICT_4X4_100), комплементарный EKF фильтр с одометрией.
  - Управление: встроенный Web UI на порту 8080 (Server-Sent Events, виртуальный джойстик, редактор маршрутов Pure Pursuit).

### 2. СТРУКТУРА ПРОЕКТА И ОСНОВНЫЕ ФАЙЛЫ
- firmware/esp32_stepper_driver/esp32_stepper_driver.ino — прошивка ESP32 (Arduino C++).
- termit_api.py — промышленный Python API модуль связи с ESP32, кинематика Omni, одометрия, watchdog.
- localization_node.py (и localization_node_remote.py) — главный ROS 2 узел навигации, слияния данных меток и колес, алгоритм Lookahead Pure Pursuit, веб-сервер (порт 8080) с 2-секундным таймером авто-снятия тока с обмоток.
- video_tag_detector_remote.py — ROS 2 узел детекции ArUco через камеру Raspberry Pi (libcamerify).
- start_termit.sh — скрипт запуска всей системы на Raspberry Pi в фоновом режиме.
- deploy_to_pi.py — скрипт синхронизации файлов с ПК на Raspberry Pi по SSH/SFTP.

### 3. ТЕКУЩИЙ СТАТУС СИСТЕМЫ
- Навигация ArUco + одометрия работают стабильно.
- Маршруты выполняются плавно по алгоритму Lookahead Pure Pursuit с точкой упреждения (Carrot point) без застреваний.
- Реализовано управление питанием моторов: кнопки «Подать ток» / «Снять ток» в UI, автоматическое снятие тока через 2 секунды после последней команды и на финише маршрута.

### 4. КЛЮЧЕВАЯ ЗАДАЧА: РЕШИТЬ ПРОБЛЕМУ С МОТОРАМИ («ЗАКУСЫВАНИЕ» И ПРЕРЫВИСТАЯ РАБОТА ПРИ РАЗГОНЕ)
Симптомы:
При разгоне с места и смене скоростей шаговые моторы работают прерывисто, с микрорывками, акустическим дребезгом или ступенчатыми подергиваниями («заглючивают при разгоне»).

Глубокий технический анализ причин проблемы:
1. Архитектурный недостаток прошивки ESP32 (библиотека AccelStepper):
   - В текущей прошивке шаги генерируются методом stepper.runSpeed() внутри void loop().
   - runSpeed() НЕ использует аппаратные таймеры или прерывания! Он программно опрашивает micros().
   - В том же самом void loop() выполняется Serial.available(), чтение и парсинг sscanf(), отправка телеметрии одометрии Serial.printf() на скорости 115200 бод (20 раз в секунду), проверка watchdog и авто-сна.
   - Из-за блокирующих операций с UART и вычислений время одного прохода loop() колеблется от 40 мкс до 1500–2500 мкс (джиттер времени цикла).
   - Для шагового двигателя при частотах 300–1000 шагов/сек интервал между импульсами составляет 1000–3300 мкс. Джиттер в 500–1500 мкс приводит к неравномерности следования тактовых импульсов (timing pulse jitter), срыву синхронизации ротора, механическому резонансу и ощущению «закусывания» и «прерывистой работы».

2. Рампа разгона рассчитывается на хосте (Python), а не на контроллере:
   - Python-поток termit_api._control_loop() на частоте 40 Гц отправляет команды 's <f> <r> <l>\n' по UART.
   - Каждая посылка перезаписывает _stepInterval в AccelStepper.
   - Задержки USB-UART буфера на Linux/Raspberry Pi приводят к тому, что команды приходят не строго через 25 мс, а пачками (bursts), вызывая рывки ускорения.

ЧТО ТРЕБУЕТСЯ СДЕЛАТЬ:
1. Перевести генерацию шагов на аппаратные таймеры ESP32:
   - Использовать библиотеку FastAccelStepper (наиболее стабильная библиотека для ESP32, использует встроенные аппаратные таймеры / RMT / MCPWM периферию).
   - В FastAccelStepper импульсы шагов формируются аппаратно с точностью до долей микросекунды независимо от void loop(), Serial и загрузки процессора.
   - Аппаратная поддержка разгона/торможения (трапециевидная или S-curve рампа с заданием setAcceleration) прямо на ESP32!
2. Оптимизировать протокол управления:
   - Контроллер ESP32 сам плавно выходит на целевую скорость моторов с заданным аппаратным ускорением.
   - Raspberry Pi отправляет целевые скорости только при их изменении, без необходимости бомбардировать UART 40 раз в секунду.
3. Сохранить всю существующую функциональность:
   - Одометрия 20 Гц (передача абсолютных шагов p1, p2, p3 и скоростей s1, s2, s3 в формате o ...).
   - Команды Enable/Disable токов (e 0 / e 1).
   - Watchdog безопасности (w <timeout_ms>).
   - Авто-сон/снятие тока через 2 секунды.
